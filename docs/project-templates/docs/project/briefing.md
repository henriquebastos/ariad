# Project Briefing

Stable context for this project.

Use this document for premises that should not be re-explained or re-litigated in every agent session. Keep it concise enough that an agent can read it at the start of meaningful work.

## Purpose

What does this project exist to do?

Name the value, audience, and reason for the project in plain language.

## Current State

Where is the project now?

Include the stage of development, what is working, what is incomplete, and what kind of work is currently most important.

## Architecture Premises

What technical or structural decisions shape the work?

List stable premises such as language, framework, storage model, deployment model, runtime constraints, integration boundaries, or important design choices.

## Product Premises

What product assumptions should guide implementation?

Include target users, user experience constraints, positioning, non-negotiable behaviors, or quality expectations.

## Constraints

What should the agent respect?

Include hard constraints, style constraints, compatibility requirements, privacy rules, performance expectations, or things that should not be changed casually.

## Operating Notes

How should work happen in this project?

Include project-specific commands, test expectations, branch or commit habits, release notes, or validation requirements.

## Glossary

Define project-specific terms the agent should understand.
