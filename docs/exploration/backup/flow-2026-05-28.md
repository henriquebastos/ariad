# Exploratory Flow

This document describes how Ariad Exploratory Mode moves in practice.

It is intentionally separate from the [Conceptual Model backup](conceptual-model-2026-05-28.md). The conceptual model names the entities and principles. This flow describes the process by which exploration begins, thickens, and eventually becomes promotable or archived.

The flow is not a linear pipeline. Exploratory work can loop, branch, pause, weaken, or intensify. The flow names common movements so the Driver and Navigator can recognize what is happening.

## Flow overview

The flow moves across three main exploratory surfaces:

```text
Signal Radar
  possible signals, captured signals, and signals kept for later

Narrative Field
  active Exploratory Stories and their thickening material

Candidate Gate
  promotable Exploratory Stories or candidates ready for Navigator decision
```

A common path is:

```text
signal captured
  -> Exploratory Story opened
  -> story thickens
  -> clusters / resonance / attractors appear
  -> inquiry opens
  -> hypotheses form
  -> experiments learn
  -> candidate forms
  -> candidate promoted or archived
```

A shorter path is valid when the signal is already clear:

```text
signal captured -> candidate formed -> Delivery Mode
```

A longer path is valid when the field remains ambiguous.

## Step 1. Signal capture

Exploration begins when a thin signal is captured.

A signal is a small narrative worth preserving before it has enough meaning, evidence, or direction to guide delivery.

```text
Users abandon checkout after the address step, but we do not know why.
```

Signal capture has two entry paths:

```text
Navigator-expressed signal
  the Navigator explicitly says something that behaves like a signal

Driver-detected signal
  the Driver notices a possible signal inside the conversation or work context
```

The default policy is:

```text
Detection can be inferred.
Capture should be visible.
Persistence should initially require Navigator expression, explicit keep-for-later intent, or exploratory engagement.
```

### Event

```text
signal_captured
```

### What changes

When a signal is captured, it becomes part of the journey's Signal Radar.

No delivery commitment is created.

No roadmap item is created.

No task is created.

When the Driver only detects a possible signal, nothing is persisted yet. The Driver may show a subtle hint and wait for the Navigator to either explore it now or keep it for later.

### Minimum record

```text
id
journey
summary
source
captured_at
state: captured
commitment: none
```

### Driver behavior

Signal capture should be lightweight, visible, and reversible.

For a Navigator-expressed signal, the Driver may capture directly and acknowledge that no delivery commitment was created.

For a Driver-detected signal, the Driver should not persist by default. It should show a subtle Signal Hint inside the response. If the Navigator keeps it for later, the signal enters Signal Radar without opening an Exploratory Story. If the Navigator explores it now, the Driver may capture it and open the path toward the Narrative Field.

The experience should not feel like a form or a task manager.

### User-facing acknowledgement

For a captured signal:

```text
Signal captured: users abandon checkout after the address step, but we do not know why.

No delivery commitment was created.
```

For a detected but not yet captured signal:

```text
△ Possible signal
Checkout abandonment may be tied to address validation.

Is this relevant? Tell me more to explore it now, or say “keep for later”.
```

### Open questions

- What threshold makes a perception worth a Signal Hint?
- What threshold makes a Navigator expression sufficient for direct capture?
- Should “keep for later” create a captured signal with a different state than active exploration?
- Should the Driver ever persist detected signals without explicit keep-for-later intent or exploratory engagement?
- Should the Driver always show capture acknowledgement, or can some captures be batched into a later review?
- Should the initial signal summary preserve the user's wording, the Driver's distilled wording, or both?
